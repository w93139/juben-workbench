# 产品方向调整与分阶段改进方案

状态：2026-10-03 策略方案，尚未实施、尚未作为新版本验收结论。

## 一、结论与本轮边界

建议继续开发现有工作台，但先重定交付物，再分批改造；暂停把“自动生成整本、模型交叉审查、通过快照 ZIP”作为新项目的默认完成路径。现有材料处理、拆解、蓝图、版本和预算能力有保留价值，无需重建产品。当前最值得验证的新交付物是**可编辑、可追溯、可交给外部作者或 Agent 执行的策划交接包**。

依照本轮已经讨论并确认的方向，本方案默认：前段拆解与蓝图可继续使用当前已接入的模型 API，但任何新的付费调用仍须单独预览并按既有授权闸门执行；**正文写作和交叉验证阶段只输出方案、任务书及核验清单，不在应用中调用模型 API**。用户也可完全手工整理前段内容。此处“不接 API”指后两段，不改变现有模型配置、费率或历史账本。本轮仅形成方案，不变更应用逻辑、数据、权限或部署。

## 二、现状与证据边界

| 部分 | 当前进度 | 新方向中的判断 |
|---|---|---|
| 材料读取与拆解 | 本机文件读取/OCR、长输入分段、来源引用、方向建议已实现；M6 已有真实整本拆解联调 | 保留，强化来源核对与作者修订 |
| 蓝图 | 九类节点编辑、草稿和历史、字段及引用静态检查已实现；M6 记录了真实蓝图调用的契约与超时修复 | 保留，先核对已有真实蓝图，再验证新交付形式；静态检查不能证明剧情可玩 |
| 正文与交叉审查 | 六类正文、两路独审、互审、复核和恢复链路完成工程测试 | 作为旧项目历史能力保留；新项目默认不触发这些付费调用 |
| ZIP 与备份 | 完整作品 ZIP 只接受服务端“审查通过”快照；浏览器项目 JSON 备份已实现 | 新增独立的策划交接包；不能把旧 ZIP 改名或把蓝图检查标为审查通过 |
| 验收 | M0–M5 的自造材料、假供应商和浏览器回归已通过；M6 的真实整本完成与用户验收未见通过记录 | 工程通过、真实作品可用、真人试玩继续分开记录；真人试玩为 `not-run` |

依据：[当前能力与开发边界](02-当前能力与开发边界.md)、[开发计划](05-后端开发计划.md)、[当前验收清单](06-当前验收清单.md)、[前端任务记录](../03-前端原型/TASK.md)。当前任务记录末尾是 M6 蓝图调用修复，没有新的真实整本通过快照及试玩结论。已有交接中提及一版真实蓝图的结构检查结果，正式采用前仍应从本机保存记录和来源逐项核对，不能据此宣称整本作品已完成。

## 三、新产品的完成定义

面向“有现成素材、需要改成原创可玩的剧本杀”的创作者，工作台完成以下四段工作：

1. **材料与证据**：导入文件、OCR、记录来源位置和不确定识别；把可核对事实与原文摘录分开。原件保持在本机，不因方案导出而自动打包。
2. **拆解与大纲**：整理人物、事件时间线、秘密、线索、冲突和已有玩法；给出待核对点与若干改写方向。作者能修订大纲和方向，保留版本及来源，不只是在模型建议中选一个按钮。
3. **原创蓝图**：形成可编辑的角色关系、事件、知情范围、主张、线索、轮次和结局等九类结构，并标记“继承事实／拟改写／原创设计／待确认”。引用检查负责结构完整性，原创性、合理性和体验判断交给作者。
4. **写作与验证交接**：输出逐件正文写作任务书、跨件约束、两名独立审读者的检查任务、互审与统稿流程、问题回填方式和人工试玩清单。默认状态明确写为“正文未生成／交叉验证未执行／真人试玩 `not-run`”。这些是**执行方案**，不写成完成报告。

策划交接包应是单独版本化的导出物，可包含：项目范围与创作约束、材料目录及来源定位、拆解摘要与作者修订、正式蓝图、角色/轮次/道具等写作任务卡、交叉核验清单、未决问题与状态清单。建议首版同时提供便于人阅读的 Markdown 和便于工具读取的 JSON；只纳入用户已保存、明确选择导出的内容。玩家可见与主持人专用信息在结构上分开，不能把秘密混进玩家交付文件。原始材料默认不入包。

“可交接”的标准是结构齐全、来源可追、任务边界清楚、未决问题显式列出；它**不是**“已改写完成”“审查通过”或“可以开本”。用户可把包交给 Codex、其他 Agent 或真人作者，但外部写作结果与外部验证结论须重新导入或人工记录后才有相应状态；首版无需 MCP 接口。

## 四、为什么先改交付契约，再改页面

现有第 4 步的动作与资格围绕正文和审查：页面提供“开始交叉验证／导出完整档案”，完整作品写目录的路由依赖服务端 `validationId` 和通过快照。仅隐藏按钮或修改标题会留下错误的导出资格及状态含义。还需要处理以下契约：

- **项目状态**：新增“策划交接已就绪／已导出”的状态，和旧的“审查通过”分开；策划包永远不继承完整作品 ZIP 的通过资格。
- **导出与信任边界**：首版在浏览器本地从已保存的 IndexedDB 项目状态组装策划包并下载，校验 schema、引用、包版本及所用项目修订指纹；现有服务端不能直接读取浏览器状态。若后续要由服务端写入选定目录，须另建路由，验证提交内容与本次已确认快照，不能借用旧的 `validationId` 或接受浏览器自报“审查通过”。保留旧通过快照 ZIP 的既有语义，旧项目成果仍可查。
- **数据兼容**：保留现有存储键、项目备份 v1–v4 的恢复及旧审查/正文/费用记录。新增字段与包版本采用兼容迁移，恢复副本不自动获得新的执行或导出资格。
- **费用与入口**：实施新方向时，页面移除正文/审查启动入口，同时服务端拒绝新的 `review` 费用预览与启动请求，防止绕过页面发起后段付费调用；旧任务状态查询、旧正文/审查和账本仍可读。前段保留费用预览、累计额度、保守预留、异常费用核对和每次付费确认。原 M6 的调用上限是预留上界，不是实际账单或新产品单价。
- **验收语言**：蓝图静态检查只可显示“结构检查通过”；正文、交叉审读、统稿及试玩各有独立的 `not-run / 进行中 / 有问题 / 人工确认` 状态，绝不自动提升为作品通过。

## 五、建议执行顺序与每批出口

| 批次 | 工作 | 完成证据 |
|---|---|---|
| 0. 保全基线 | 暂停继续原 M6 的新正文/审查付费运行；核对现有真实项目的蓝图、未决费用和备份可恢复性。不得读取或提交整本原文、密钥或运行账本 | 基线与待核对项记录；没有新增付费调用、原数据可读 |
| 1. 定义交付物 | 用自造材料做一份策划交接包样例；确定大纲修订、来源引用、写作任务卡、核验清单、保密分层、导出格式与状态规则；同步修订 PRD、能力边界、开发计划和验收清单的目标表述 | 用户可检查一份样例包及逐项验收标准；旧能力与新目标清楚区分 |
| 2. 改造应用 | 增加作者可编辑大纲及版本；调整四步导航与第 4 步；从已保存浏览器状态独立导出交接包；服务端阻断新的 `review` 预览和启动，旧正文/审查成果保留只读入口，旧完整作品导出不被重定义 | 新旧项目均不能发起新的后段模型调用；旧任务与备份可读且不丢内容；策划包内容、来源修订、保密分层和版本验证通过 |
| 3. 真实项目试用 | 在已有授权材料上核对拆解与蓝图，导出交接包给一位实际创作者按任务书尝试；按修订后的清单逐项记录“通过／未测／失败及原文”，真人试玩继续 `not-run` 直到发生 | 可追溯的包、作者反馈、未决问题、真实费用和所用时间；不拿模型自评代替用户验收 |
| 4. 按需求扩展 | 若交接试用确有反复手工搬运，再考虑外部成果导入、CLI 或 MCP；均围绕同一业务服务与权限边界设计 | 有具体使用场景、接口合同与权限检查后才排期 |

第 1 批通过后即可开始第 2 批，不必等待旧“整本自动生成”跑通。第 0 批若发现待核对费用或备份问题，先处理记录与恢复，再做任何新付费操作。代码改动按仓库既有流程逐批验证、独立审查和同步；本方案本身不批准新的付费调用、配置或部署变更。

## 六、修订后的验收重点

| 验收点 | 最低要求 |
|---|---|
| 来源可靠性 | 任一关键情节/人物事实能回到材料位置；OCR 错误与推断标注；缺失来源不伪造引用 |
| 大纲可控 | 作者可改方向、结构和待确认项，保存后重新打开不丢失；旧版本可辨认 |
| 蓝图可用 | 九类结构及关联检查无阻断；仍需作者对因果、动机、玩家信息和原创程度人工判断 |
| 写作任务书 | 每件正文有目标、输入蓝图范围、玩家/主持可见性、禁止泄露点、输出要求与验收条件 |
| 交叉验证方案 | 独审、互审、统稿和试玩检查的负责人/顺序/问题回填方式明确；未执行项一律 `not-run` |
| 导出与兼容 | 新包能打开、版本及文件清单正确；旧项目、备份、费用与旧 ZIP 资格不被破坏；无原件/密钥/账本意外入包 |
| 成本 | 新后段模型调用数为 0；前段费用按每次实际预览和账本核对，失败/待核对费用不当作免费 |

## 七、主要风险与决策点

- **蓝图成本和稳定性仍需实测**：M6 的长调用、结构回显、长度及引用问题已逐项加固，但不能据工程修复宣称新蓝图稳定可用。先复核一份已有真实蓝图，再决定是否拆成更小的生成单元；拆分不得绕过费用预览。
- **产品价值取决于交接质量**：若外部作者仍需重新读完整材料、重建人物与轮次，工作台没有节省关键工作。第 3 批应观察交接包能否减少返工，并记录实际修改点与用时。
- **策划包不是成品**：对用户的入口、状态、导出文件和说明都要明确“待写作、待验证”，避免误售为可玩的完整剧本。
- **旧数据须可读**：停用新项目后段自动调用不等于删除旧成果；若未来要永久移除旧链路，应在真实试用后单独决定迁移及保留期限。

建议现在进入第 0–1 批的产品与数据保全工作，暂不直接大改代码。只有交接包样例和新验收标准站得住，才开始第 2 批实现；届时最小改造现有工作台，比重写项目更稳妥。
