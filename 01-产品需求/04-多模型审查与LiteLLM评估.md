# 多模型交叉审查与LiteLLM接入评估

日期：2026-09-08。状态：方案补充，未接入真实模型；不改变当前纯前端Mock范围。

## 1. 结论

LiteLLM适合在未来作为后端的统一模型接入层。当前先完成创作和审查的模拟交互，不安装LiteLLM、不把整份源码复制到Next.js项目。现有juben-design Skill继续作为剧本设计与审查依据，LiteLLM只负责连接模型。

目前已有审查阶段入口、历史双模型报告，以及AI／静态／模拟／真人四类检查的展示边界；自动双审、意见对比、分歧处理和复查尚未开发。本文件把这些细节补入后续C／D阶段计划，不能理解成已完成接口接入。

## 2. 是否需要API

| 使用方式 | 是否需要本产品接API |
|---|---|
| 当前Mock演示两份模型意见 | 不需要，使用明确标注的预设数据 |
| 作者去模型网站审查，再手动保存报告 | 不需要自动调用API；报告导入也仍需后续开发 |
| 点击工作台按钮，自动让两个模型检查并返回结果 | 需要后端调用模型服务接口，可用云模型或自部署模型服务 |

LiteLLM不提供免费的模型算力。云模型仍需可用账号、密钥与相应额度；真实模型密钥只保存在服务端，不进入前端、Mock或LocalStorage。成本与部署在真实接入阶段单独确定。

## 3. 放到创作流程的哪里

前台已调整为五个主步骤，不单独增加“双模型审查”步骤。蓝图检查从第三步“设计故事”进入，正文检查位于第四步“生成与检查”；底层九个阶段标识和已有记录继续保留。

| 入口 | 本次检查什么 | 开发安排 |
|---|---|---|
| 原创蓝图完成后，正文生成前 | 因果和时间线、角色贡献、必要结论能否取得证据、轮次和资源规则 | C准备版本与入口，D实现模拟双审 |
| 第四步中正文生成后的检查区 | 正文与蓝图是否一致、私人信息和谜底隔离、线索与主持指令是否可执行 | D实现模拟双审、问题处理与复查 |

两个入口使用同一套审查记录。审查中心统一展示目标对象与版本，能区分“蓝图v1的检查”和“正文v2的检查”。试玩结论仍由第五步“试玩与导出”记录；允许先导出标注未试玩的试玩包，再记录真人反馈并修订。

建议交互：

1. 选择检查范围，固定本次资料和版本，显示采用的Skill／审查规则版本。
2. 两个模型分别检查同一份资料。首轮不提前看到对方答案。
3. 分别展示两侧的等待、运行、完成或失败状态；一侧失败保留另一侧结果，支持重试失败侧。
4. 汇总共同问题与意见分歧。每条问题包含严重程度、证据位置、理由和建议。
5. 对分歧进行有限轮次互审；不能解决的保留为待作者决定，不能无限循环。
6. 作者选择采纳、暂定或不采纳，留下理由；采纳建议先预览受影响内容，再应用修改。
7. 修改产生新版本。旧结果仍绑定旧版本，受影响部分标记“需要复查”。

两模型一致不是事实证明，必须核对来源和规则；“AI审查完成”也不等于静态检查通过或真人试玩通过。模拟界面应直接标注“模拟双模型审查”，历史样例保持历史标签。

蓝图严重问题应在生成前展示并提醒修订；导航到下一页不会自动清除问题或标记完成。是否将特定严重问题设为真实生成的硬门槛，在C／D的具体规则中按问题类型细化，当前不新增阻断。

## 4. 后续需要的数据与服务

以下为建议，当前未新建这些实体或服务实现：

| 实体 | 最小信息 |
|---|---|
| ReviewRun，一次审查 | 项目、蓝图／正文及版本、资料快照、Skill／提示模板版本、模拟／真实来源、状态、时间 |
| ModelReview，一个模型的一次意见 | 所选模型、实际执行模型、轮次、结果、错误、用量及费用（不可获得时为空，不填假值） |
| ReviewFinding，审查问题 | 类型、严重程度、来源位置、各模型意见、一致／分歧、处理状态、受影响内容 |
| ReviewDecision，作者的处理 | 关联问题、采纳／暂定／不采纳、原因、采用的修改及结果版本 |

业务Service提供开始审查、读取进度、取消、重试失败侧、保存决定和发起复查。组件只调用Service；先做Mock适配器，以后替换真实API。后端负责任务持久化、幂等、版本冲突和取消语义，不能让网络超时造成重复计费和重复保存。

跨模型故障回退须记录实际模型。两个审查者最终都调用同一个模型时，不能宣称“双模型独立审查完成”；共用缓存也不能把同一份答复当成两次独立意见。仅对证据位置和JSON结构校验成功，不代表推理正确。

## 5. LiteLLM能帮什么

| 能力 | LiteLLM适合承担 | 本项目仍要承担 |
|---|---|---|
| 连接模型 | 多供应商请求／响应转换、流式响应 | 作者和审查者的职责、Skill与资料范围 |
| 调用稳定性 | 超时、限流、重试、故障回退 | 整个创作任务的恢复、部分成功、版本与产物保存 |
| 用量管理 | 调用用量、成本记录、预算与虚拟密钥等能力 | 项目预算策略、费用提示和作者操作权限 |
| 输出格式 | 按供应商能力传递结构化输出要求 | 字段校验、事实来源、时间线与线索规则 |
| 审查 | 把请求转给各模型 | 独立审查、分歧比较、人工决定、修改影响与复查 |

能力依据：[LiteLLM介绍](https://docs.litellm.ai/)、[Router](https://docs.litellm.ai/docs/routing)、[结构化输出](https://docs.litellm.ai/docs/completion/json_mode)。它不是剧本领域审查器，也不能替代OCR材料审计和真人试玩。

未来建议结构：

```text
当前Next.js界面
  → 本项目Service／后端API
  → 审查任务执行器（Skill、资料版本、双审和分歧处理）
  → 可替换的模型接入适配器
  → LiteLLM Proxy
  → Kimi、DeepSeek等模型服务
```

如果后续采用Python执行任务，也可以在执行器中用LiteLLM Python SDK。仅接两个兼容接口时，直接写轻量服务端适配器也可行；为保留选择，应先隔离模型调用层，不为了LiteLLM提前更换前端技术栈。

## 7. 建议顺序与验收

1. C完成蓝图编辑和版本，D完成模拟双审与问题处理。验收一致意见、分歧、单侧失败、重试、作者决定、修改后旧结论失效，以及历史／模拟／真人的区分。
2. 进入真实后端阶段时，再决定供应商账号、预算与运行位置；接入可替换的模型适配器，按需要启用LiteLLM。
3. 用小份测试材料核对真实调用、实际模型记录、费用、超时、取消和结构校验，再扩展完整剧本。真实结果不得与Mock记录混用。
